# Kiwi Project Coding Guidelines

This document integrates CSS, JavaScript, and React best practices for the Kiwi portfolio management application. All code should follow these standards.

---

## JavaScript Standards

### Variables and Types
- **Use `const` by default** — only use `let` when the value will be reassigned
- **Use strict equality (`===`)** — avoid `==` which performs type coercion
- **Use semicolons** in regular JS logic (optional at end-of-line due to ASI, but recommended)
- **Use `let`/`const`, never `var`** — `var` is outdated

Example:
```javascript
const portfolioName = 'Growth Fund'  // const — value fixed
let activeTab = 'portfolios'         // let — value changes
```

### DOM Manipulation
- Use `document.querySelector()` and `document.querySelectorAll()` to find elements
- Use `textContent` for plain text (safe), `innerHTML` only for trusted HTML
- Use `classList.add()`, `classList.remove()`, `classList.toggle()` for CSS class management
- Use `addEventListener()` to register event handlers
- **Never build `innerHTML` from untrusted user input** — security risk

Example:
```javascript
const card = document.querySelector('.portfolio-card')
card.classList.add('selected')
card.style.backgroundColor = 'lightyellow'
```

### Template Literals
Use backticks for string interpolation:
```javascript
const message = `Hello ${name}`
```

## React Standards

### Components
- Build reusable, functional React components
- Use React hooks (`useState`, `useContext`, etc.) for state and side effects
- Components should be focused and single-responsibility
- Props should be clearly named and documented

### State Management
- Use `useContext()` for global application state (e.g., authentication)
- Use `useState()` for local component state
- Keep state as close to where it's used as possible

### Routing
- Use `react-router-dom` for client-side navigation
- Organize routes by feature or page
- Use `useNavigate()` for programmatic navigation

### API Integration
- Create a dedicated API client module (`kiwiApi.js`)
- Include authentication headers (Bearer tokens) in all API requests
- Handle errors gracefully with user-friendly messages
- Use `async`/`await` for asynchronous operations

Example:
```javascript
async function fetchPortfolios(token) {
  const response = await fetch('/api/portfolios', {
    headers: { 'Authorization': `Bearer ${token}` }
  })
  if (!response.ok) throw new Error('Failed to fetch')
  return response.json()
}
```

## CSS Standards

### Selectors
- **Use class selectors for styling** — avoid IDs for CSS (IDs are for JavaScript hooks)
- **Element selectors** — use sparingly for styling all instances of an element
- Follow the specificity rule: ID (highest) > class > element (lowest)
- Keep specificity low to maintain CSS maintainability

### Rules
```css
/* element selector — lowest specificity */
p {
  color: #333;
}

/* class selector — medium specificity, preferred for styling */
.card {
  background-color: #fff;
  border-radius: 8px;
}

/* id selector — highest specificity, reserved for JavaScript hooks */
#submit-btn {
  font-size: 1rem;
}
```

### The Cascade
- Later rules override earlier rules (at equal specificity)
- More specific selectors always win
- Avoid fighting the cascade with overly specific rules or `!important`

### Properties and Units
- Use semantic HTML elements (`<button>`, `<nav>`, `<main>`) for structure
- Use relative units (`rem`, `em`, `%`) over absolute units (`px`) when possible
- Use meaningful color names or variables (e.g., `#333` for dark text, `#fff` for white)
- Maintain consistent spacing and padding using a scale (e.g., 8px/16px/24px/32px)

### Layout
- Use Flexbox for one-dimensional layouts
- Use CSS Grid for two-dimensional layouts
- Keep media queries organized and at the end of the file

## Project-Specific Best Practices

### Frontend (React + Vite)
- Store authentication tokens securely (localStorage with `kiwi_` prefix)
- API requests should include Bearer token from stored token
- Auto-create backend user record on first login
- Load security/ticker prices from backend API before executing trades

### Component Structure
```
frontend/src/
├── pages/          # Full-page components (LoginPage, DashboardPage, etc.)
├── components/     # Reusable UI components (PortfolioList, HoldingsTable, etc.)
├── auth/           # Authentication logic (OIDC, token management)
├── api/            # API client and data fetching
├── config.js       # Environment variables and configuration
└── index.css       # Global styles
```

### Security
- **Never expose API keys in frontend code** — keep them in `.env` (backend only)
- **Verify JWT tokens on the backend** — do not trust frontend token validation alone
- **Use PKCE for Authorization Code Flow** — protects against code interception
- **Always validate user input** before sending to backend
